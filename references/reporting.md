# 报告结构

对话简报：
- 开头说明本次查询起止日期及显示时区；不同来源区间不同则说明总范围，并在覆盖摘要列出差异。
- 按卖家相关性给出通常 3–5 条核心信息，不足不凑数。每条含“发生什么/适用于谁/何时发布或生效/原文链接”。可附很短的影响解释，建议有依据才加。
- 明确官方事实、媒体报道、个人经验或推断。标题避免制造赚钱保证。
- 末尾说明覆盖缺口和本地完整报告链接，并写“想调整时间范围，直接告诉我；也可以让我展开某一条。”

完整 HTML 报告：
1. 查询日期、生成时间、画像相关筛选条件（不重复暴露不必要个人信息）。
2. 重要新信息：事实、来源类别、原文链接、发布时间/编辑时间/生效时间（未知就写未知）、美国适用范围、关联影响。建议另列且从简。
3. 可选的历史参考：明确日期及为何仍有用。
4. 覆盖表：来源组、实际起止时间、已读入口/检索词、成功/部分/失败、限制和待查区间。
5. 下次继续任务及证据限制。未发现值得报告的新信息时直说，不复述旧内容充数。

不要把抓取时间当发布时间、把网页编辑时间当生效时间、把未找到证据写成没有变化。未经完整正文核实的线索可列待核实，不列成确定政策。原文摘要用自己的话，避免大段转载。

## 通俗易懂

面向普通卖家写作，先说明发生了什么，再说明和卖家有什么关系。用短句、具体例子和日常用词；必要的英文术语首次出现时用中文解释。比如把“对履约时效产生影响”写成“可能影响你按时发货”，把“优化利润结构”写成“看看这项费用会不会让你少赚”。保留准确的金额、条件、时间和不确定性，不为通俗而省略关键限制。信息为主，建议为辅。

## HTML 与自动打开

- 生成可直接打开的完整 UTF-8 HTML 文档，包含 `<!doctype html>`、`<html lang="zh-CN">`、`<meta charset="utf-8">`、移动端 viewport 和有意义的标题。
- 使用内联 CSS、清晰标题和段落、易读字号及适配窄屏的排版；无需构建工具、外部字体、CDN 或 JavaScript，离线也能阅读报告正文。
- 来源使用可点击的 HTTPS 链接。网页原文作为文本转义后写入，不把来源 HTML、脚本或事件属性直接拼入报告。
- 保存并成功提交后，主动使用宿主自带的文件预览/浏览器打开最终 HTML；没有此能力时使用操作系统的默认浏览器打开能力。用工具的结构化路径参数，或将路径作为独立参数传入，避免拼接不受信任的 shell 文本。每次报告只请求打开一次，不必再询问用户是否打开。
- 若无法打开，提供可点击的本地 HTML 文件链接并简短说明原因。只在工具确认后说已打开；仅发出请求时说“已请求打开”，不声称用户已经看到页面。打开失败不等于报告保存失败。
