# 报告写作

## 先筛选，再写报告

每条候选在内部回答三个问题：
1. 依据够不够？已读到支持这项具体结论的正文，政策和费率有官方依据，日期和适用条件没有张冠李戴。
2. 对当前经营有什么具体关系？能联系到已知类目、售价、阶段或关注问题；画像未知时只保留广泛适用的信息，条件表达，不猜测用户情况。
3. 相比上次多了什么？新规则、新细节、新证据、临近的相关截止日期或必要更正。仅重复旧内容不算新增价值。

不满足的候选留在内部，不为每个来源留一个位置，不追求条数。一次只找到一条有用信息，就只写一条。

具体边界：
- “学院补查完毕”“未发现新课程”“社区人数增长”“采集成功”不是卖家情报，不入正文。
- 普通低价商品卖家通常不需要高额成交免佣信息；不得靠“以后可以卖高端套装”制造关联。画像或当次问题确实相关才纳入。
- 只看社区标题不能推导“公认”“主流”“影响有限”等结论。一个已读案例只能作为一个案例，且有具体可用经验才值得收录。
- 没有发布日期不等于没有更新；找不到信息不等于没有变化。
- 地区、类目、卖家资格、运输服务等适用条件按原文核实。美国市场不代表某条物流服务一定适用；不清楚时不写“直接影响你的运费”。

## 像给熟悉的卖家写一份简短来信

上面的筛选问题只供内部思考，不是输出栏目。默认用讲清重点的小标题和自然段落写作，不套“发生了什么 / 和你有什么关系 / 建议 / 依据”等逐条问答格式；也不要换成“核心变化 / 经营影响 / 行动建议”继续套同样的格式。

文章标题随内容拟定，朴素具体即可，不要求固定写某一句。标题下用一行小字交代关注日期范围和时区。日期范围不代表穷尽所有来源。多条内容时可以用一句话引出最值得留意的事；只有一条短消息时直接进入正文，避免开头摘要、标题和首段重复三遍。

按价值排序，不按来源分组。通常一个具体的小标题加一两段就能讲完一件事，但不规定段数和字数：简单消息一句话即可，复杂规则可以多解释必要条件。标题本身要传递事实，例如哪项费用有调整、哪项功能开放给谁，不写“重磅利好”“运营赋能”等空泛措辞。

正文先说值得知道的事实，再自然接上必要的背景、条件或实际影响。每段只推进一个意思；相关性已经显而易见时，不另写“这对你很重要”。不要反复以“作为一名……卖家”“对于你的店铺而言”开头。信息不支持建议时，到事实为止，不强行以“建议关注”“抓住机会”“提前布局”收尾。

排版由内容决定：
- 一条消息用自然段；只有真实并列的多个事项才用列表，需要比较档位/方案时才用表格，有先后顺序的操作才用步骤。
- 金额、截止时间或必要条件可少量加粗，不要每句话都加粗。短报告不需要“一、二、三”的大纲和重复结语。
- 不给每条消息配同样的卡片、彩色标签和栏目。优先舒适的阅读宽度、留白和轻量分隔，让正文成为视觉重点。
- 在相应段落后附简短原文链接，例如“官方说明 · 发布日期”，无需单独立“依据”小节。媒体或个人经验在正文或来源文字中明确身份；推断则直接写成“这可能意味着……”，不能藏在标签里。
- 来源链接指向支持具体结论的原文。发布日期未知就不编造，可明确标注核实日期。`<details>` 只收纳较长的佐证细节，不隐藏适用范围、限制条件或会改变理解的重要信息。

**更正要清楚，不要写成检讨模板。** 标题可用“更正：……”并直接写出被更正的事实；在正文中简短交代上次说法哪里不准确、正确条件和实际影响，不再拆成三个栏目。条件未知时不要替用户判断。更正不是新政策，不用“平台最新调整”包装。

历史参考只在理解当前消息确有必要时简短带入，并标原日期。不默认附上次报告回顾、已处理信息清单或下一轮研究任务。

末尾用一句自然的话提醒可以更改时间范围或追问，不要求逐字使用统一话术。对话中提供已保存的 HTML 链接，必要时点出最值得看的事，不复制整份报告。

没有可用信息时简短说明这次暂时没有可供整理的新信息，稍后可以再看。不声称“没有政策变化”，不填旧内容。

第一次编写或发现文字仍像填表时，读 [写作正反例](writing-examples.md)。示例仅展示表达方式，不是事实来源或必须照搬的新模板。

## 内部记录与事实边界

来源覆盖表、检索词、错误、待查区间、哈希、采集数量、执行用时、几分钟前检查过、存储目录和下次补查任务仅进入私有运行记录，不放入 HTML 或对话。来源缺失不展示，但政策条件、经验样本等事实本身的限定不能隐去。

原文摘要用自己的话，避免大段转载。未经正文核实的线索留在内部待核实，不在用户报告里设“待核实消息”区。

## 写完后再读一遍

按普通卖家日常阅读的习惯润色：用“发货”“费用”“少赚多少”等具体词，必要英文术语首次出现时解释；保留准确的金额、时间、条件和不确定性。不要为追求口语而写成夸张推销，也不使用生硬的公文表达。

交付前通读全文，检查：有没有几段反复说同一件事？是否每条都机械重复某些标签或句式？删掉某句后有没有少任何有用信息？建议是否真的从证据和用户需求中得出？把重复和空话删掉，把条件放回相关句子。只保留值得读的内容，不为显得报告完整而加栏目。

## HTML 与自动打开

- 生成可直接打开的完整 UTF-8 HTML 文档，包含 `<!doctype html>`、`<html lang="zh-CN">`、`<meta charset="utf-8">`、移动端 viewport 和有意义的标题。
- 使用内联 CSS、清晰标题和段落、易读字号及适配窄屏的排版；无需构建工具、外部字体、CDN 或 JavaScript，离线也能阅读报告正文。
- 来源使用可点击的 HTTPS 链接。网页原文作为文本转义后写入，不把来源 HTML、脚本或事件属性直接拼入报告。
- 保存并成功提交后，主动使用宿主自带的文件预览/浏览器打开最终 HTML；没有此能力时使用操作系统的默认浏览器打开能力。用工具的结构化路径参数，或将路径作为独立参数传入，避免拼接不受信任的 shell 文本。每次报告只请求打开一次，不必再询问用户是否打开。
- 若无法打开，仅提供已保存的本地 HTML 文件链接，静默记录原因。只在工具确认后说已打开；仅发出请求时说“已请求打开”，不声称用户已经看到页面。打开失败不等于报告保存失败。

## 静默降级

采集及执行错误只供 Agent 内部判断，不向用户展示报错、技术诊断、失败网站清单、VPN 建议或重试过程。某来源不可达时继续查其他来源，不为一个来源反复重试而拖延报告。成功信息少就少给，不凑数；无可用信息时使用上面的简短提示，不把获取失败解释为没有更新。

HTML 保存失败时可直接在对话交付已核实内容，不提供不存在的文件链接，也不声称已保存。自动打开失败时保留文件链接即可。事实本身的不确定性（例如生效日期未知、个人经验不代表普遍情况）仍如实表达，不将不确定信息写成确定事实。用户主动要求排查时，再按需解释内部记录。
